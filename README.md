# Dental Backend — AWS Serverless API

A cloud-native appointment backend rebuilt as an AWS serverless application. The project demonstrates how a small backend can be designed for low operational overhead, least-privilege access, automated validation, and scalable managed services.

## Architecture

```text
Client
  |
  v
API Gateway (HTTP API)
  |
  v
AWS Lambda
  |
  v
DynamoDB
  |
  +--> CloudWatch Logs
```

## API

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | Service health check |
| POST | `/appointments` | Create an appointment |
| GET | `/appointments` | List appointments |

Example request:

```json
{
  "patientName": "Example Patient",
  "date": "2026-09-01",
  "time": "10:00"
}
```

## Infrastructure

Terraform provisions:

- API Gateway HTTP API
- AWS Lambda
- DynamoDB with on-demand billing
- DynamoDB point-in-time recovery
- DynamoDB server-side encryption
- Lambda IAM execution role
- Least-privilege DynamoDB permissions
- CloudWatch-compatible Lambda logging

The Lambda deployment package is generated by Terraform using `archive_file`, avoiding a manually committed binary ZIP.

## CI

GitHub Actions runs:

1. Node.js tests
2. Terraform formatting check
3. Terraform initialization without a backend
4. Terraform validation

No AWS access keys are required for the validation workflow.

## Local validation

```bash
npm test
cd terraform
terraform init
terraform fmt -check -recursive
terraform validate
```

## Security decisions

- No credentials are stored in source code.
- Lambda receives only the DynamoDB permissions required by the API.
- DynamoDB encryption and point-in-time recovery are enabled.
- Infrastructure changes are reviewed through Git before deployment.

## Production next steps

For a real clinic deployment, add authentication/authorization, input/schema validation, appointment conflict checks, encryption with a customer-managed KMS key where required, structured audit logging, API throttling, WAF where appropriate, alarms, backups/retention policies, and a remote Terraform state backend.

## Why this project matters

This repository is intentionally small enough to understand end-to-end while demonstrating cloud engineering fundamentals: serverless architecture, managed databases, IAM, Infrastructure as Code, automated testing, and operational thinking.

> This project is a technical portfolio/demo system. It is not designed to store real patient health information without additional privacy, compliance, access-control, and audit requirements.
